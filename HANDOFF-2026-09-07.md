## Goal

Finish Issue #71's Rust UI migration and Issue #75's native runtime path without
claiming a feature is complete until its renderer, transport, runtime, and real
target evidence agree. PR #63 at `d9deb7b3` is green; this isolated branch is
`agent/pr63-ui-runtime-parity` for the next implementation slice.

## Do not lose these boundaries

- `optn-core -> optn-app -> optn-runtime -> optn-transport -> optn-ui` stays
  one-way. Renderers dispatch typed `AppAction`s and read `AppState`; they do
  not own wallet balances, history, signing, network policy, or platform rules.
- Preserve React/Capacitor until a matching Rust path has real-target evidence.
  The existing watch-only SeedCash flow is still the behavioral reference.
- The browser extension is `AppSurface::Extension`: a constrained read-only
  viewer with Home, Assets, Receive, and History. It must remain unable to
  prepare, sign, or broadcast a spend until a separately designed secure
  lifecycle exists. Do not give it desktop-native USB, Tor, clipboard, camera,
  or background-service powers by accident.
- Chipnet only for any live check. Never read, print, or use a recovery phrase,
  private key, or funded-wallet material from files or the environment.
- Do not present native chain sync, SHV/MMR verification, Tor-routed transport,
  hardware signing, PSBT signing, SeedCash round-trip, or CashFusion as live
  merely because a screen/model exists. Trace the host call and runtime first.

## Visual source of truth

Use `docs/ui-overhaul/` exactly, especially `A_home_single.png`,
`D_actions_collapsed.png`, `L_send_bch.png`, and `N_receive.png`. Issue #71
explicitly forbids inventing a second visual language for the Rust renderer.

Desktop and mobile share the same state/actions/feature rules. They use
different shell composition:

- mobile: fluid device width, safe-area bottom navigation, 44px targets;
- desktop: a normal resizable/maximizable window, rail, wider content grid,
  split portfolio/activity panels, and no stretched mobile card.

Do not add a second desktop/mobile/extension flag system. The existing shared model is:

`FeatureFlags` decides product permission, `transport_support(surface)` describes
physical transports, `hardware_vendors_for(surface)` intersects transport with
an integration declaration, and the renderer reads that result. CashFusion is
desktop-only because it needs its long-lived service. Hardware may be enabled
on mobile only when a real host provider exists; a grey state must explain that
the integration is absent, not falsely claim that a phone cannot use hardware.

All new work is Rust only: Rust core, Rust runtime, Rust transport, Rust-to-WASM,
and native Tauri providers. There is no new TypeScript, handwritten JavaScript,
browser QR/camera/clipboard helper, or duplicate front-end store. The Tauri
transport previously had a handwritten `inline_js` invoke shim; this branch
replaces it with Rust `js_sys` access to the existing Tauri global.

## Changes started in this worktree

- Desktop Tauri window now opens at `1280x820`, remains resizable/maximizable,
  and keeps a `720x560` usable minimum. This removes the phone-shaped desktop
  default without affecting shared app logic.
- `AppTransport` now has a typed `write_clipboard` capability. The Tauri WASM
  adapter calls the existing `clipboard_write_text` Rust command; it does not
  use `navigator.clipboard` or a new JS bridge.
- `optn-ui/src/qr.rs` adds a local Rust QR SVG encoder for receive addresses.
  It contains one unit test and does not call a remote QR service.
- `ReceivePage` now renders the local QR, offers typed Tauri copy with an
  explicit unsupported/error result, shows a disabled Share control, and marks
  token receiving as unavailable until the token projection is wired.
- `WalletHome` now has a `wallet-home` hook for the desktop/mobile canonical
  grid CSS still to be completed.
- Native chain transport now uses the shared `optn_core::tor` route decision:
  core-defined loopback is the only direct exception; selected remote Electrum,
  BIP37, and Neutrino routes use their existing Rust SOCKS adapters only after
  the default Tor proxy passes the SOCKS verification; remote full-node RPC and
  event adapters stay fail-closed because their current implementations cannot
  consume that route. `BchnRpc`/`BchnZmq` are names of the present adapters,
  not a BCHN-specific architecture requirement: the runtime model remains node
  neutral. Six focused chain-runtime tests cover the no-dial, Tor-route, and
  unsupported-adapter boundaries without touching a remote endpoint.
- The Tauri-free CLI now uses the same core route decision. It skips Tor probing
  for loopback endpoints, refuses remote plaintext Electrum at construction,
  and otherwise opens each remote Electrum connection only through a freshly
  isolated Rust SOCKS route. The local SOCKS capability probe remains shell I/O;
  the policy itself remains in `optn-core`. `tokio-socks` is pinned in the CLI's
  own lockfile. The CLI test suite passed with 110 tests, including the no-direct
  fallback and fake-proxy guards.

The QR dependency is now pinned in `Cargo.lock`. Re-run the WASM and Tauri

## Next implementation order

1. **Rust first:** trace and complete the native runtime path before more UI
   polish. `NativeChainRuntime` currently creates a `ChainService` but does not
   project a verified refresh into authoritative `AppState`; it also rebuilds
   only from legacy server fields and `ConnectionPolicy::auto()`. Use the
   durable `UserNetworkOverlay`, explicit transport policy, verified evidence,
   and a typed projection before a renderer says that it is synced.
   Do not remove the remote deny gate to make a connection work. The existing
   Rust SOCKS adapters are now wired for Electrum/BIP37/Neutrino and preserve
   proxy-side hostname resolution. The desktop and CLI currently use the same
   core decision with shell-local default 127.0.0.1:9050/9150 probes; move that
   route selection into a typed durable transport policy before adding custom
   proxies or mobile-managed configuration. Current full-node RPC/event adapters remain
   unavailable remotely until each has a verified proxy-capable implementation;
   do not treat the `Bchn*` adapter names as a node-brand architecture model.
2. Verify the hardware backend against the shared capability model. Native
   Ledger/Trezor command modules exist, but a UI/model flag is not evidence of
   a complete device account/signing lifecycle. Extension and mobile remain
   disabled until their own host provider is wired and tested.
3. Complete canonical CSS/markup for `WalletChrome`, Home, Actions, Receive,
   and Send from the reference screenshots only after the typed state it shows
   is real. Use `.shell-desktop` and `.shell-mobile`, not an arbitrary shared
   breakpoint that stretches mobile.
4. Make basic Actions buttons dispatch the existing Send/Receive routes. Show
   unavailable Swap/Connect/Scan/CashFusion states as disabled with accurate
   reasons until their native route exists.
5. Preserve Send's integer-satoshi parser until a tested exact BCH-decimal
   parser exists in shared Rust. Never use float conversion for money.
6. Trace legacy SeedCash Prepare -> Sign -> Broadcast behavior into typed Rust
   transport/runtime before removing React: animated `crypto-psbt` frames,
   density, fullscreen, bad-frame accumulation, signed-PSBT import, validation,
   and policy-routed broadcast all need real implementations.
7. Treat Issue #75 separately from visual polish: native runtime currently does
   not project provider events into wallet state or prove the full SHV/MMR/Tor
   transport path. Do not mark it end-to-end before that bridge exists.
